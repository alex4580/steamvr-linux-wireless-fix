I reproduced the native Linux Base Station 2.0 wireless update/recovery crash with **SteamVR 2.17.10 stable (25330290) and 2.18.2 beta (25664061)**, and isolated two concrete memory errors in the beta binaries. A controlled local repair then completed one replacement station's MCU update from 3002 to 3008. The stock binaries remain unmodified.

This adds evidence to this issue and related #709 / #589; I am posting once here because the scan-vector destruction stack matches the failure examined below. It does not establish that every historical report has these exact causes.

**System:** CachyOS x86_64, Linux 7.2.9-1-cachyos, native Steam client build 1788652215, Index HMD, two Base Station 2.0 units, `sniper_platform_3.0.20260805.254768`. SteamVR beta was tested; Steam client beta opt-in was not verified. Native Bluetooth sleep/wake already worked.

**Reproduction:** enable Bluetooth, start the replacement station's wireless firmware update or recovery, and continue through scanning. `vrmonitor` aborts on the `BaseStationWork` thread with an invalid free or `std::bad_alloc`. Controllers-off and generating a system report first did not fix it. Expected behavior is a completed update or a recoverable error, without terminating SteamVR.

**1. ZIP entry ABI mismatch.** The firmware reader in `libnrfserlib.so` at module offset `0x5ebc0` expects a 260-byte filename layout and reads the uncompressed length at record `+0x130`. `GetZipItem` instead writes a 4096-byte filename layout, total size `0x1030`, with the length at `+0x1028`. In the saved core, the latter contains the correct BIN size of 297956 bytes; the caller reads 139716371572944 and passes it to allocation. This also writes beyond the caller's stack record. A hardware-isolated harness reproduces the original crash without any headset. Redirecting the two relevant call sites through a layout adapter in a separate copy makes the original reader return all three archive entries byte-for-byte correctly, including repeated reads and the missing-archive error path.

**2. Cross-module empty-string ownership.** In the separate post-scan crash, a scan record's string field at `+0x20` points into `libnrfserlib.so`'s static empty COW-string storage (data `+0xebc58`, header `+0xebc40`). `vrmonitor` compares against its own singleton (`+0x39f5c0`), then decrements and attempts to free the foreign static storage. The invalid-free path is around `vrmonitor+0x17f0f8..0x17f5b3`. This remains unfixed in the experiment; only the replacement station was powered and controllers were off to avoid the observed trigger.

**3. Additional DFU handoff timing evidence.** After repairing ZIP parsing, SteamVR authenticated and received `20 01 01`, but requested local disconnection less than 1 ms after queuing the indication confirmation, then timed out reaching the bootloader. A process-scoped shim preserving API arguments, return values, and errors delayed one matching disconnect by 500 ms after successful confirmation on attribute 28. With that change, the bootloader became reachable and the update completed. Nordic's [reference updater](https://github.com/NordicSemiconductor/pc-nrfutil/blob/master/nordicsemi/dfu/dfu_transport_ble.py) waits for peer disconnection; the [API](https://github.com/NordicSemiconductor/pc-ble-driver/blob/master/include/sd_api_v6/ble_gattc.h) describes confirmation success as queued transmission. This supports a lifecycle/timing problem, not a universal 500 ms requirement. The observed disconnect event was a connection timeout, so I cannot claim a clean peer-disconnect sequence or the exact over-air order.

**Verification:** all 75 logged DFU CRC responses match Valve's unchanged archive: 144 init bytes and 297956 firmware bytes. SteamVR reported wireless success. After restarting the unmodified installed runtime, OpenVR reported firmware 3008 and no update available on both stations, with successful property queries. Both were detected and slept normally afterward. No firmware bytes or authentication were modified.

The source-only community package is exact-build gated and operates on a separate SteamVR copy; the user still initiates Valve's own updater. The underlying repair was tested on **one CachyOS/Index system and one replacement-station update**. The packaged wrapper has not performed an additional firmware update. It does not repair the empty-string defect or provide a general recovery guarantee. Selected anonymized evidence is in the repository; the release contains the fuller report, filtered logs, and backtraces. Full cores are retained locally, not publicly uploaded.

Could Valve confirm the ZIP structure definitions and empty-string ownership against the matching source builds, and fix the confirmation/disconnection lifecycle in the native Linux wireless updater? Consistent ZIP metadata layouts and C++ object ownership are needed; allocation caps or permanently disabling Bluetooth would not address these findings.
